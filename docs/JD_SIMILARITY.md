# JD 相似度与上游借鉴口径

复核日期：2026-10-22；代码快照 `d2d695d`。计算入口：`python scripts/jd_similarity.py`（可加 `--json`）。
本文回答两个问题：这批招聘 JD 与本项目的方向重合/实现覆盖有多高；本项目从相关热门项目里各借了多少。

## 1. 口径

- “JD”指 `data/manifests/jd_review.json` 里 70 条冻结记录（19 家公司；核心 51、相邻 18、待核验 1；实习 28、校招 14、社招 28），共 486 个能力标签。
- 相似度不是单一分数，本文并列三个指标，避免用一个数字冒充结论：
  - **覆盖深度**：每条 JD 的能力标签按实现深度加权后取均值（0–1）。
  - **二值覆盖**：深度 ≥0.6 的 (JD, 能力) 对占全部标签对的比例。
  - **方向重合**：项目主赛道 9 项能力集合与 JD 能力集合的 Jaccard。
- 深度权重是**登记判断**，不是测量值；脚本把权重写在代码里，便于复核和修改。同一套标签压成 1/0.5/0 三档时整体约 0.52；本文保留深度分，以免把“薄实现”和“子场景”抹平成满分。

| 能力 | 深度 | 依据 |
|---|---|---|
| metric | 0.85 | 原生指标、提取、Wilson/Bootstrap 有实现与离线测试 |
| calibration | 0.75 | 样本级配对 Bootstrap、每种子差值、协议完整性拒绝 |
| data | 0.75 | 固定 dev、长度分层、等预算选样、SFT 导出 |
| contamination | 0.70 | 精确/近重复/同源检查；只覆盖可见数据 |
| diagnosis | 0.70 | 训练池逐样本诊断驱动 B2，门禁拒绝缺诊断 |
| benchmark | 0.60 | 接入 6 个公开 benchmark，不自建新 benchmark |
| longctx | 0.60 | RULER 式 4K/8K/16K 本地诊断，不是官方榜单 |
| code | 0.45 | 仅 HumanEval+ pass@1，无 Code Agent |
| training | 0.45 | 仅 LoRA SFT，不涉及预训练/中训练 |
| platform | 0.35 | 薄 Harness，无调度/Web 产品 |
| judge | 0.25 | 仅辅助错误分析，不进入指标 |
| agent | 0.05 | 轨迹评测由 retail-agent-eval 承接 |
| safety / multimodal | 0.00 | 明确非目标 |

## 2. 结果

| 分组 | n | 覆盖深度 |
|---|---|---|
| 全部 JD | 70 | **0.425** |
| 核心 JD | 51 | 0.437 |
| 相邻 JD | 18 | 0.387 |
| 实习+校招 | 42 | 0.409 |
| 实习/校招中的核心岗 | 28 | 0.425 |
| 社招 | 28 | 0.448 |
| 剔除多模态/代码/长上下文 | 70 | 0.461 |
| 只看项目承接的 9 项能力（主赛道） | 68 | **0.625** |
| 悲观 / 乐观（每项 ±0.15） | 70 | 0.306 / 0.575 |

- 方向重合 Jaccard：全部 0.342、核心 0.352、实习+校招 0.320、社招 0.377。
- 二值覆盖 0.407；29.4% 的能力标签属于多模态/安全/Agent 等背景或非目标，这是整体分被拉低的主因。
- 单条京东 JD（JD-18，算法开发岗-具身大模型评测研究）覆盖 **0.445**，与全部 JD 均值接近。
- 分布：17 条 ≥0.50，26 条在 0.40–0.50，14 条在 0.35–0.40，8 条在 0.30–0.35，5 条 <0.30；32 条 ≥0.45，43 条 ≥0.40。
- 公司均值范围 0.333（字节跳动）–0.500（智谱），样本量 1–20 条不等，公司间差异不应过度解读。

## 3. 差距结构

70 条里有 59 条至少要求一项当前项目的明确非目标能力（Agent、多模态、安全、平台化、Code Agent）。各能力的损失份额：

| 能力 | JD 频次 | 项目深度 | 损失 |
|---|---:|---:|---:|
| agent | 49 | 0.05 | 46.6 |
| platform | 58 | 0.35 | 37.7 |
| multimodal | 37 | 0.00 | 37.0 |
| safety | 30 | 0.00 | 30.0 |
| code | 45 | 0.45 | 24.8 |
| training | 42 | 0.45 | 23.1 |
| benchmark | 56 | 0.60 | 22.4 |
| judge | 27 | 0.25 | 20.3 |
| 其余 6 项（diagnosis/metric/data 等） | — | — | 34.4 |

合计 486 个标签、损失约 276 个（56.8%）。**差距主要来自岗位要求的广度，而不是评测方法本身**：metric、calibration、data、diagnosis、contamination 这 5 项方法学的损失合计只有 31.6 个（6.5%）。

如果补短板，提升空间大致如下（每项单独改一个等级，是能力覆盖的算术上限，不是承诺）：

| 调整 | 覆盖深度 |
|---|---:|
| platform 0.35 → 0.8（真正做调度、看板、CI） | 0.487 |
| agent 0.05 → 0.5（把 retail 的轨迹评测并进来） | 0.469 |
| safety 0.00 → 0.7（独立安全/对抗评测） | 0.467 |
| training 0.45 → 0.9（真实 SFT 并接回闭环） | 0.461 |
| judge 0.25 → 0.8（专用 Judge 训练与校准） | 0.451 |
| 五项都补 | 0.636 |
| 再加多模态 0.5、代码 0.8 | 0.711 |

## 4. 热门项目借鉴量

统计对象：`src/` + `scripts/` 共 2,264 行 Python（快照 `d2d695d`）。**上游源码零复制**：`external/` 不随仓库分发，按 `references.lock.yaml` 拉取；下表“可归因代码行”指语义来自上游、由本项目重写/适配的行数，按函数边界统计。

| 借鉴对象 | 复用方式 | 可归因行 | 占 2,264 行 |
|---|---|---|---|
| lm-evaluation-harness | GSM8K 提取语义、任务协议、`check_upstream_gsm8k.py` 逐样本对拍 | 90 | 4.0% |
| IFEval 官方规则 | `verify_instruction` 覆盖 19/25 条指令类型 | 54 | 2.4% |
| NVIDIA RULER | niah_single_1/niah_multikey_1/vt 任务语义 + 本地生成器 | 53 | 2.3% |
| EvalPlus | HumanEval+ 测试与 `check(candidate)` 契约、受限执行 | 50 | 2.2% |
| LlamaFactory | YAML/`dataset_info.json` 配置与 messages 数据格式 | 42 | 1.9% |
| LoRA（论文） | rank32/alpha64/lr1e-4 等超参 | 0 | 0 |
| vLLM | 仅运行时服务，无代码适配 | 0 | 0 |
| HELM / OpenCompass / VLMEvalKit / EvalScope | 未借鉴（只出现在 JD 原文里） | 0 | 0 |

合计可归因约 289 行，**12.8%**；其余约 87% 是协议、选样、统计、报告与治理代码。分“依赖程度”看则是另一幅图：训练执行 100% 交给 LlamaFactory，HumanEval+ 测试 100% 来自 EvalPlus，6 个任务里 4 个（GSM8K/MMLU-Pro/BBH/IFEval）的评分与提取以 lm-eval-harness 为参考实现并逐样本核对。也就是说，**借鉴集中在“协议与执行”，自研集中在“受控对照与可追溯性”**。

按“能力份额”粗估（±5pp，不是代码行测量）：公开 benchmark 数据 17%、Qwen3 基座 10%、lm-eval 8%、LlamaFactory 7%、vLLM/HF 5%、EvalPlus 4%、IFEval 3%、RULER 3%、论文 2%，合计外部约 **59%**；自研（固定 dev、分层、B1/B2、Token 匹配、冻结、清单、污染、统计、报告）约 **41%**。代码行 87% 自写与能力份额 41% 自研并不矛盾：模型、数据、训练执行、测试集来自上游，评测协议与治理是自研。

不声称：直接复制上游代码、改进上游框架、复现官方榜单、把 LlamaFactory/EvalPlus 说成自研。

## 5. 结论

- 对 70 条 JD 的整体相似度约 **0.43**，方向上约三分之一重合；在项目自己承接的赛道里约 **0.63**。准确说法是“方向一致、深度有限”，不是“高度匹配”。
- 单条京东 JD 约 **0.45**；换公司/岗位会在 0.16–0.60 间波动，差距主要来自多模态、安全、Agent、平台化要求。
- 上游借鉴约 **13% 代码行**，且以协议/测试/配置为主；核心资产是 B1/B2 等预算对照、冻结协议与失败保留，这部分不依赖任何上游项目。
- 岗位匹配上，基座评测/预训练后训练评测/数据选择/评测诊断（JD-12、29、30、34、51、54、64）对得上方法学；Agent 轨迹评测需要并上 retail 项目；多模态、安全对抗、Code Agent 评测差距明显。

## 6. 表述边界

可以如实写：

> 基于 Qwen3-8B/4B-Base，在 GSM8K/SVAMP/MMLU-Pro/BBH/IFEval/HumanEval+ 上按固定 completion 协议测量；自研固定 dev 留出、长度分层、B1/B2 等预算选样、Token 匹配、冻结协议、污染检查、配对统计和失败保留；训练用 LlamaFactory，代码评测用 EvalPlus 测试。

不要写：

- “自研 benchmark / 自研评测框架 / 自研训练框架 / 预训练研究”
- “提升 X%”——真实训练和评测还没跑，目前只有离线契约与 fixture 闭环
- 把公开 benchmark 说成自己构建的；说“在 GSM8K 官方 train 上固定留出 500 dev”更准确
- 把本地 RULER 诊断说成官方榜单，或把 LLM Judge 当主评分

## 7. 限制

- 深度权重、主赛道集合都是登记判断；换一套权重，绝对值会变，排序与缺口结论相对稳定。
- 未做语义向量或人工双盲标注；`jd_review.json` 的能力标签本身也是研究产物，可能有漏标。
- 借鉴比例按代码行估算，不含数据集、任务定义和运行时依赖；说“13%”不等于“只用了 13% 的上游工作”。
- 所有数字都是离线估算，不构成真实模型效果或岗位匹配的因果结论。
